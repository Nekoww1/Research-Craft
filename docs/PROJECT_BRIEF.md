# 项目构想与内容原则

记录日期：2026-10-20。本文保存建仓前后讨论形成的项目方向，供新 session 接续。它不是已经完成的课程，也不是固定技术方案。

## 1. 项目目的

用户希望收集科研工作者关于研究与学术写作的方法、经验和案例，将它们分析、分类、融合，形成自己可以持续使用的科研方法参考项目，并通过前端流畅展示。

主题可以是“如何培养一个 PhD”或“如何成长为独立研究者”。这些是内容主线的例子，最终的副标题、读者分层和课程范围尚未锁定。

内容编写者需要站在熟悉多位研究者思想的教师视角，考虑后辈应该先理解什么、如何获得判断力、怎样采取行动。用户授权代理承担具体章节和小节的编排，前提是遵循这里保存的内容原则。

个人精读仍有价值，但项目不以用户先读完所有来源为启动条件。用户希望先将这些知识组织成可以使用的前端项目，再在后续学习和实践中深化。

## 2. 用户原始构想：完整工作范围

1. 收集科研方法与写作经验文章、报告、课件等材料。
2. 分析材料，粗略定位其关注的问题与适用范围。
3. 分类文章，理解各来源可以帮助解释什么。
4. 汇总概念并进行归纳、融合，识别概念之间的关系。
5. 选择一条概念主线，例如“如何培养一个 PhD”，构建完整的科研方法论介绍。
6. 以前端形式展示，形成流畅的阅读和理解体验。
7. 在合适的位置附原文案例与引用，让读者知道具体讲解源于哪篇方法论材料。
8. 以熟悉前人多种思想的专家视角进行教学，重新编排讲述顺序、章节与小节，提供解释和执行指导。
9. 充分利用 HTML 的表现能力，使用图形、模块、对照、字体层次等形式帮助理解。

用户计划公开维护并同步到 GitHub，也提出可以借助 GitHub 建立在线页面。这是用户的第一个 public GitHub 仓库。

## 3. 已确认的内容要求

### 3.1 必须能够指导行动

内容需要帮助读者判断应该怎样做，并解释原因与条件。章节摘要、概念罗列和经验口号不能独立构成完整教学。

行动指导的形式由内容决定，可以是判断步骤、案例复盘、文本修改过程、实验安排或其他合适的方法。无需给所有模块统一配置一种表单或清单。

### 3.2 不同模块采用不同构造

用户明确举出的两个方向：

- 研究 taste：更多结合案例，展示判断依据与研究选择。
- 论文写作：更多使用模板、批注和修改前后对照。

实验、阅读、合作或长期规划等其他模块的形式，需要依据实际来源与教学内容再确定。它们尚未有固定结构。

### 3.3 先完成正文，再设计可选的引入问题

用户对早期建议作出了明确修正：

> “可以像书引一样每一个小节讲述前给个小问题，引发读者思考，但是这个应该在整个章节文章编写完成以后，再思考如何提出这个问题。”

执行含义：

- 章节的概念关系、前置知识和教学目标决定内容与顺序。
- 正文完成后，再考虑是否适合设计一个简短的引导性问题。
- 用户允许这种引入方式，但没有要求每个小节必须以问题开头。
- 读者跳过问题，仍应能够完整、连贯地阅读正文。
- 代理自拟的问题不自动代表读者普遍存在的真实困惑，也不能被用来证明某个教学主题重要。
- 问题应该能被正文真正回应，避免诱导性前提或空泛发问。

早期“每个小节围绕一个真实困惑展开”的建议已修正，不能作为项目固定模板继续执行。

### 3.4 来源应在教学发生的位置可追溯

适合的位置包括概念解释、原文案例、观点对照或图解的邻近区域。具体呈现方式由界面设计决定。

不要为原文补造作者当时的想法、未知情况、失败尝试或动机。真实来源没有提供的过程，可改写为明确标注的教学示例，或保留为未知。

### 3.5 融合时保留观点的身份和条件

需要分清：

- 作者原有的意见、案例与论证。
- 编辑者基于多个来源作出的综合解释。
- 为教学自行构造的示例。
- 用户后续实践产生的记录与修订。

对不一致的观点，应解释其关注层次、适用条件或实际分歧；不能仅因希望章节流畅就将它们写成共同结论。

### 3.6 视觉呈现服务于讲解

用户明确希望采用多样形式，避免页面只承载连续的文字摘要。可根据实际内容使用概念图、过程图、案例展开、观点对照、模板批注、图表或交互模块。

字体大小、重点标记与排版帮助建立信息层次。具体图形和交互是否加入，由它是否帮助读者理解、比较或行动来决定。

## 4. 内容组织的工作模型

以下模型是代理提出、符合已确认原则的工作建议；仍可在实际编写中调整。

### 4.1 三种内容相互关联

| 内容 | 保存什么 | 用途 |
| --- | --- | --- |
| 来源记录 | 作者、原始链接、材料类型、阅读范围、定位与缺口 | 保持准确性并方便返回原文 |
| 概念与关系 | 概念含义、来源之间的互补与分歧、适用条件 | 为跨来源综合提供依据 |
| 教学正文 | 教学顺序、解释、案例、具体指导与视觉呈现 | 形成可连贯学习的课程和可查阅的参考 |

三者首先是编辑上的区分，不意味着必须立即设计数据库或复杂系统。

### 4.2 连贯学习与按需查阅

讨论中曾把“个人长期查阅”和“新人系统学习”列成二选一，用户指出需要解释两者的关系。后续澄清：两者可以共享同一内容体系，只是进入路径不同。

建议保留按成长路线连续阅读的路径，并允许按概念或当前需要直接进入相关内容。用户尚未确认哪种场景是首页的首要入口，不能将个人优先或新人优先视为已定方案。

### 4.3 可探索的能力主线

以下只是候选能力框架，尚未成为正式章节目录：

- 判断问题为什么值得研究，培养研究 taste。
- 理解已有工作，识别真正的未知。
- 将模糊直觉转化为可以检验的主张或研究问题。
- 设计实验，解释结果，并据此修正判断。
- 写清贡献、方法与证据，进行有效学术交流。
- 将多项工作积累成连贯的研究方向。

避免把列表直接扩展成全部页面骨架；正式目录应基于来源研究与教学编排形成。

## 5. 执行路线

### 已确认的整体方向

收集材料 → 分析与定位 → 分类 → 概念汇纳 → 围绕主线编排教学 → 前端展示 → 在对应位置加入案例和引用。

其中，引导问题的设计顺序必须在正文编写之后；模块构造需随内容变化。前端是项目主要交付，应让真实内容与界面逐步结合。

### 建议的首轮范围，尚未单独确认

可以先做一个完整样章，例如“从兴趣到一个值得研究、能够开始的问题”，贯通来源分析、概念综合、教学编排与前端展示，再扩展其他章节。

这是代理提出的起步建议，不是用户已经批准的唯一范围，也不意味着只交付一章即完成整个项目。开始执行时，结合新 session 的明确任务决定首轮范围。

### 建议的完成判断

- 读者能够沿正文理解关键概念及其关系。
- 内容在需要处给出具体做法和适用条件。
- 案例、原文观点和编辑综合有清楚的身份与来源。
- 视觉与交互帮助理解实际内容。
- 用一个真实研究或写作任务阅读试用后，能够指出获得了哪些判断依据，哪些内容还需修订。

这些是设计判断依据，不是已经开展过用户测试的结论。

## 6. 尚未确定的事项

- 正式内容副标题、首要受众、首页入口及读者分层。
- 最终章节目录、首轮实现范围和纳入来源的数量。
- 前端技术栈、视觉风格与具体交互形式。
- 是否使用 GitHub Pages，以及构建和发布方式。
- 是否保存来源全文、保存方式和公开展示范围。
- 是否加入个人笔记、练习或学习进度功能；目前没有实现这些功能的明确要求。

后续代理可在已授权范围内提出具体方案并承担编排。涉及实质范围变化时再与用户对齐；不要逐项重复询问已经明确的原则。
